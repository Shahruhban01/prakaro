# Moderation Queue Management & Custom Form Engine

## 1. Queue Architecture & Atomic Codes

Prakaro's moderation console enables supervisors and administrators to configure dedicated moderation queues tailored to specific operational priorities (e.g. general search discovery, user reports, airport/transit hubs, high-traffic commercial zones, AI escalations).

Each queue has an atomic identifier code generated by `ModerationCounter`:
- Format: `QUEUE-<KIND>-<000>`
- Examples: `QUEUE-GENERAL-001`, `QUEUE-REPORT-002`, `QUEUE-AI-003`

### Queue Kinds
- `GENERAL`: Standard search discovery verification.
- `AI`: Cases where Gemini / OpenRouter flagged low confidence, ambiguity, or suspected private amenity.
- `ACCESS`: High-risk access verification (e.g. gated residential vs public commercial).
- `REPORT`: User problem reports submitted from the mobile driver app.
- `REVERIFY`: Periodic re-verification of stale records whose verification validity period has elapsed.
- `QA`: Dedicated quality assurance audit sampling queue.

## 2. Visual Rule Builder Specification

The queue routing engine uses a deterministic boolean expression tree evaluating candidate facts against queue criteria:
- **Maximum Nesting Depth**: 3 levels.
- **Maximum Group Children**: 5 conditions per group.
- **Boolean Operators**: `AND` (all conditions must match), `OR` (at least one condition must match).
- **Comparison Semantics**:
  - String fields (`category`, `source`, `status`, `access`, `pricing`, `evidence`, `ai`, `region`, `classification`): Strict equality (`==`).
  - Numeric fields (`demand`, `priority`): Greater-than-or-equal (`>=`).

### Example Rule JSON
```json
{
  "op": "OR",
  "children": [
    {
      "field": "category",
      "value": "NEW_FACILITY_VERIFICATION"
    },
    {
      "op": "AND",
      "children": [
        { "field": "source", "value": "SEARCH" },
        { "field": "demand", "value": "2" }
      ]
    }
  ]
}
```

## 3. Dynamic Review Form Builder

Queues can define bespoke review forms to collect structured field observations from human moderators.

### Supported Question Types
1. `BOOLEAN`: Strict tri-state selection (`YES`, `NO`, `UNKNOWN`).
2. `SELECT`: Single choice from a defined options list.
3. `MULTI`: Multi-select from a defined options list.
4. `TEXT`: Short-text observation.
5. `NUMBER`: Strict numeric entry (e.g. capacity count).
6. `DATE`: Strict ISO-8601 calendar date.
7. `EVIDENCE`: Citation of an approved evidence item ID attached to the case.
8. `REASON`: Structured justification code.
9. `NOTES`: Long-form freeform markdown comments.

### Conditional Dependencies
Questions can conditionally appear based on prior question answers using the `when: { key: string, equals: string }` predicate.

## 4. Atomic Task Leases & Collision Prevention

To prevent concurrent moderators from reviewing or modifying the same task simultaneously:
1. **Claiming**: `POST /api/v1/moderation/cases/:id/claim` updates `owner = a.userId`, sets `status = 'IN_REVIEW'`, and grants a **30-minute lease** (`leaseUntil = now + 1800000ms`).
2. **Conflict Prevention**: If a task has an active lease held by another user, any claim attempt immediately returns `HTTP 409 Conflict` with `MODERATION_CONFLICT`.
3. **Lease Expiration**: If a moderator abandons a task or their session expires, `leaseUntil` lapses, and any authorized staff member in that queue can claim it.
4. **Release**: `POST /api/v1/moderation/cases/:id/release` releases the lease immediately and resets the status to `QUEUED`.
